# AgentCrew — мультиагентная система на .NET

Команда LLM-агентов, которая отвечает на бизнес-вопросы по внутренним данным компании: сама планирует работу, распределяет шаги между специализированными агентами, вызывает инструменты, собирает ответ и проверяет его перед выдачей.

Демо-сценарий: аналитический ассистент вымышленной сети электроники **«ТехноЛавка»**. У него есть база знаний (стратегия, обзор рынка, логистика, маркетинг, политика возвратов) и данные продаж за три квартала 2026 года.

**Репозиторий:** https://github.com/NikTyu/agentcrew

**Стек:** .NET 10, ASP.NET Core Minimal API, [Microsoft.Extensions.AI](https://learn.microsoft.com/dotnet/ai/microsoft-extensions-ai) (`IChatClient`, `AIFunction`), OpenAI .NET SDK, Server-Sent Events, xUnit. Фронтенд на чистом JS, без сборки.

## Быстрый старт

```bash
dotnet run --project src/AgentCrew.Web --urls http://localhost:5080
```

Откройте http://localhost:5080 и нажмите один из примеров.

Ключ API **не обязателен**: без него система работает в **демо-режиме**. Вместо LLM подставляется детерминированный скриптовый клиент, а инструменты, данные, оркестрация, параллельность и цикл критики работают по-настоящему. Так демонстрация не зависит от интернета и квот.

### Подключение настоящей LLM

Подходит любой OpenAI-совместимый API. Параметры можно задать в `src/AgentCrew.Web/appsettings.Local.json` (файл в `.gitignore`) или через переменные окружения:

```bash
export Llm__ApiKey=sk-...
export Llm__Model=gpt-4o-mini
```

### Локальная модель через Ollama (полностью офлайн)

```bash
brew install ollama
ollama pull qwen3:8b
OLLAMA_NUM_PARALLEL=2 OLLAMA_CONTEXT_LENGTH=16384 ollama serve
```

В другом терминале запустите приложение с профилем `ollama` (настройки в `appsettings.Ollama.json`):

```bash
dotnet run --project src/AgentCrew.Web --launch-profile ollama
```

Почему такие параметры:
- `OLLAMA_NUM_PARALLEL=2`: без него Ollama выполняет запросы по одному, и параллельные шаги плана встают в очередь.
- `OLLAMA_CONTEXT_LENGTH=16384`: контекст по умолчанию (4K) слишком мал для промптов редактора и критика с результатами всех шагов, особенно на русском.
- `Llm:ReasoningEffort = "none"`: отключает у qwen3 режим размышлений. Вызов инструмента занимает 2,4 с вместо 16 с.
- `Crew:MaxPlanSteps = 3`: небольшие модели склонны дробить план на лишние шаги.

Замеры на MacBook (Apple M4, 16 ГБ):

| Модель | Вопрос | Время | Итог |
|---|---|---|---|
| qwen3:8b | «Почему упали продажи в Новосибирске?» | ~2 мин | Параллельный план, верные цифры и источники, одобрено с первого раза |
| qwen3:8b | «Рост выручки в Q3 и рекомендации» | ~4,5 мин | Автопроверка вернула исследователя, который ответил без поиска; итог корректен |
| qwen2.5:7b | «Рост выручки в Q3 и рекомендации» | ~3 мин | Цифры верны, но редактор добавляет «причины», которых нет в базе знаний |

Для живой демонстрации перед жюри лучше облачная модель или заранее записанный прогон. Локальный запуск показывает, что система работает без интернета и внешних API.

| Параметр | По умолчанию | Описание |
|---|---|---|
| `Llm:Provider` | `Auto` | `Auto`: OpenAI, если задан ключ, иначе демо. Также `OpenAI` или `Demo` |
| `Llm:Endpoint` | `https://api.openai.com/v1` | Базовый URL OpenAI-совместимого API |
| `Llm:Model` | `gpt-4o-mini` | Имя модели |
| `Llm:Temperature` | `0.2` | Пустое значение (`null`) — не передавать (для reasoning-моделей) |
| `Llm:ReasoningEffort` | — | `low`/`medium`/`high`; `none` отключает размышления (qwen3 в Ollama) |
| `Llm:NetworkTimeoutSeconds` | `120` | Таймаут одного запроса; локальным моделям нужен запас |
| `Crew:MaxPlanSteps` | `5` | Максимум шагов в плане |
| `Crew:MaxRevisions` | `2` | Сколько раз критик может вернуть ответ на доработку |

## Архитектура

```mermaid
flowchart TD
    U[Пользователь] -->|вопрос + история| O[CrewOrchestrator]
    O --> P[Планировщик<br/>JSON-план с зависимостями]
    P --> W1
    P --> W2
    subgraph Волна 1 — параллельно
      W1[Аналитик<br/>sales_report · compare_quarters · calculator]
      W2[Исследователь<br/>search_knowledge_base · read_document]
    end
    W1 --> W3[Исследователь<br/>шаг, зависящий от s1]
    W1 & W2 & W3 --> WR[Редактор]
    WR --> C{Критик<br/>JSON-вердикт}
    C -->|замечания| WR
    C -->|одобрено| A[Ответ]
    O -.->|поток событий SSE| UI[Веб-интерфейс:<br/>план · трасса · метрики]
```

### Как это работает

1. **Планирование.** Планировщик получает список исполнителей с описанием их возможностей и возвращает JSON-план: шаги, исполнители, зависимости `dependsOn`. Оркестратор валидирует план: неизвестный агент заменяется исполнителем по умолчанию, ссылки вперёд удаляются (так циклы невозможны), число шагов ограничено. Если ответ модели невалиден, оркестратор переходит к плану «каждый исполнитель на весь вопрос».
2. **Выполнение графа.** Шаги делятся на «волны» топологической сортировкой. Шаги одной волны выполняются параллельно (`Task.WhenAll`), зависимые шаги получают результаты предшественников во входном сообщении.
3. **Агент = ReAct-цикл** (`AgentRunner`). Модель решает, какие инструменты вызвать. Рантайм выполняет их параллельно, с таймаутом и перехватом ошибок, и возвращает результаты модели, пока не получит финальный текст. Цикл написан вручную, а не через `UseFunctionInvocation()`: так каждое действие попадает в трассу и действуют лимиты.
4. **Рефлексия.** Редактор пишет ответ только по результатам исполнителей. Критик проверяет полноту, отсутствие галлюцинаций и наличие рекомендаций и возвращает JSON-вердикт. При замечаниях черновик уходит на доработку, не более `MaxRevisions` раз.
5. **Наблюдаемость.** Всё, что делают агенты, публикуется как поток `AgentEvent`: план, старт и финиш шагов, вызовы инструментов с аргументами, результаты, рецензии, токены. UI получает его по SSE и показывает в реальном времени.

### Надёжность (guardrails)

| Риск | Защита |
|---|---|
| Агент зациклился на инструментах | `MaxIterations`, затем принудительный финальный ответ без инструментов |
| Инструмент упал или завис | Таймаут; ошибка возвращается модели текстом, и она может исправиться |
| Модель вызвала несуществующий инструмент | Ответ со списком доступных инструментов |
| Невалидный JSON от планировщика или критика | Устойчивый парсер (` ```json `, текст вокруг) и безопасный fallback |
| Агент ответил «из головы», без инструментов | Автопроверка возвращает его к работе: сначала данные, потом ответ |
| Выдуманные цифры | Каждый процент и крупное число в ответе агента и в итоговом черновике сверяются с **результатами инструментов**, а не с ответами других агентов. Несовпадение — замечание и доработка |
| Выдуманные источники | Ссылки `[документ › раздел]` должны указывать на документы, которые вернул поиск |
| LLM-критик одобряет всё подряд | Детерминированные проверки накладываются на его вердикт и снимают одобрение |
| Доработка ничего не меняет | Цикл ревью останавливается, если замечания автопроверки повторились; в UI ответ помечается как «проверку прошёл не полностью» |
| Временные сбои API (429, 5xx) | `RetryingChatClient` — middleware с экспоненциальной задержкой |
| Падение одного шага | Шаг помечается неуспешным, прогон продолжается |
| Раздувание контекста | Обрезка длинных результатов инструментов, ограничение истории диалога |
| Отключение клиента | `CancellationToken` пробрасывается до вызовов LLM и инструментов |

## Как расширить

**Новый инструмент.** Достаточно лямбды с атрибутами `[Description]`: JSON-схему для модели построит `AIFunctionFactory`.

```csharp
public static AIFunction Weather() => AIFunctionFactory.Create(
    ([Description("Город")] string city) => $"В городе {city} +5°C",
    "get_weather", "Текущая погода в городе");
```

**Новый агент.** Добавьте `AgentDefinition` в `CrewFactory.CreateDefault` и в массив `workers`. Планировщик увидит его описание и начнёт назначать ему шаги без изменения кода оркестратора.

**Другой провайдер.** Подойдёт любой `IChatClient` (Azure OpenAI, Ollama, Anthropic и т.д.). Оркестратор от провайдера не зависит.

## Сценарий демонстрации (3 минуты)

1. Покажите вкладку «Команда»: пять ролей, инструменты каждой, объём данных.
2. Запустите первый пример (рост выручки и рекомендации). На вкладке «План» видно, как аналитик и исследователь работают параллельно, а третий шаг ждёт результатов аналитика.
3. Критик возвращает первый черновик: в нём нет рекомендаций. Редактор дорабатывает ответ, второй вариант одобрен.
4. На вкладке «Трасса» раскройте вызов `compare_quarters` с аргументами и результатом, затем `calculator`: числа в ответе получены из данных, а не придуманы моделью.
5. На вкладке «Метрики» видны время, число обращений к LLM, вызовы инструментов и токены по агентам. Эти данные нужны для оценки стоимости.
6. Задайте уточняющий вопрос («А что с Новосибирском?»): история диалога учитывается.
7. Переключите `Llm:ApiKey` на реальную модель: архитектура та же, меняется одна строка конфигурации.
8. На реальной модели в «Трассе» видно, как срабатывает автопроверка («Автопроверка: ты не вызвал ни одного инструмента…»). Это хороший момент, чтобы рассказать, почему нельзя доверять LLM-критику без детерминированных проверок.
